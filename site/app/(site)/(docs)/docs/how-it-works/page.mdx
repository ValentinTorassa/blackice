# How it works

The planned parts of blackice, and what happens to one connection in ask mode.

<Planned />

## The parts

<FigArchitecture n={1} />

- **Blackice.app** has no UI and lives in `/Applications`, because macOS activates system extensions only from there. It contains the network extension and the `blackice` binary.
- **The extension** is an `NEFilterDataProvider`. It allows or drops each new flow, and in ask mode it pauses the flow until an answer arrives.
- **The daemon** runs as a LaunchAgent for the user (`blackice agent install`), receives events over XPC and runs the hooks. It takes them from the extension, which holds the configuration saved with Touch ID, never from a file.

## One connection in ask mode

<FigAsk n={2} />

Rules from `blackice.toml`, the built-in list of macOS services and current approvals are checked first, so only new destinations wait for an answer. See [Configuration](/docs/configuration). A repeated connection, with the same app, host and port, raises one event.

## Open problems

- The deciding agent needs the network to reach its model. A fixed rule for it, bound to its signature, keeps it from waiting on its own approval.
- Host names and app names come from whoever opens the connection and end up in the model's prompt. Events carry them as structured fields, and the only answers are approve and deny.
- How long macOS keeps a paused flow is not measured yet. It sets the upper bound for the timeout.
